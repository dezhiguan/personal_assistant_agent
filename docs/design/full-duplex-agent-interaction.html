DELIVERABLE / 交付顺序

先持续对话与修正，再补完整闭环

P1a 先交付持续聊天、同任务要求合并与边界 Steering；P1b 补齐状态查询、暂停/恢复/取消、多任务并发、断线重连与服务重启恢复。

BOUNDARY / 明确语义

已收到 ≠ 已生效 ≠ 已停止

运行中的工具可能已产生副作用。暂停先进入 PAUSING；取消先进入 CANCELLING。达到约定边界并核实持久状态后才发送最终确认。

PRIORITY 1 / CONTINUOUS CONVERSATION & STEERING

第一优先：持续对话，并合并同一任务的新要求

按用户最新澄清调整首期范围：既要在长任务期间正常聊天，也要让连续消息修正正在执行的同一任务。持续输入、上下文路由、要求合并和边界 Steering 一起交付。实现已于 2026-11-02 开始；下方实施记录区分已验证行为与尚未完成的验收。

FIRST DELIVERY
第一项交付

任务 A 运行时，输入框仍然可以发送。与 A 有关的补充或修正合并到 A 的最新要求；独立问题进入普通聊天。原 Deep Agent Loop 保留，不因收到消息而取消重启。后续第三句、第四句继续按上下文关联，任务结果以交付前已接收并应用的最新要求为准。

核心例子：搜索全球新闻 → 就搜索国内的就好了 → 最终交付国内新闻。第二句是对同一新闻任务的范围修正，应自动关联当前任务，无需用户复制第一句、指定 task_id 或另开任务。原始消息仍保留，生效目标更新为“搜索国内新闻”。已发出的全球查询可能返回；返回内容按国内范围筛选，不足时补搜，不继续按全球目标交付。

追加内容完整方案中的处理第一项交付的边界
普通聊天
“红眼航班是什么意思？”		进入独立聊天通道，不等待后台长任务完成，也不把旧任务计划作为本条聊天的待执行清单。优先交付 保留上下文问答，普通聊天不执行文件写入、预订或子代理任务。

查询任务进度
“任务 A 做到哪了？”		读取真实任务快照，快速返回当前步骤、工具与最近进展。完整结构化 STATUS 随任务管理交付。早期聊天只能引用已有的公开进度，不能编造新进展。
追加约束 / 修改方向
“就搜索国内的就好了。”
“预算改成 3000 元。”		依据会话上下文识别为当前任务修正，进入该任务的 STEER 控制日志；合并要求，在安全边界应用，再告知生效。优先交付 与持续聊天一起验收，不推迟到后续阶段。目标明确时自动关联；存在多个合理目标时询问。
发起另一项执行任务
“再后台整理一份资料。”		创建 B，按执行槽并发或排队，与 A 独立。完整多任务并发随 Task Manager 交付；持续聊天不等于允许任意多个工具执行流同时写共享工作区。
暂停 / 恢复 / 取消 A关联 A，经过控制状态机与安全边界确认。随任务控制交付。第一项交付只保留各条回复独立的“停止本条回复”入口，不把它称为可恢复的持久任务取消。

“持续追加”与“并行回复”的规则

  1. 接收不等待长任务。点击发送或按 Enter 后，立即在同一会话显示新问题及对应的“回复中 / 等待回复”占位。发送按钮始终表示发送，停止操作放到具体回复上。
  2. 先判断是否属于同一任务。Controller 结合消息内容、会话上下文及任务引用，区分任务修正与独立聊天。“只搜国内”修改新闻任务；“顺便解释什么是红眼航班”独立回复。任务修正更新 A 的要求，普通聊天不接管 A 的 tools、todos 或执行历史。
  3. 普通聊天有序，任务修正独立处理。同一会话只生成一条普通聊天回复；后续聊天进入有界 FIFO。STEER 不排在聊天模型回复之后等待，接收后进入控制通道，供 A 下一安全边界读取。
  4. 回复始终归属原问题。用 message_id / in_reply_to 绑定消息；生成上下文以该问题的接收位置为边界，排除未来消息和其他未完成答案。聊天完成后只更新自己的气泡，A 的进度也只更新 A。
  5. 失败和停止互不牵连。停止或出错一条聊天不取消 A；停止 A 的响应流不清空普通聊天。跨会话切换不自动停止执行；刷新、关闭页面与重启后的恢复由后续持久任务能力覆盖。

第一项交付的完成标准。既要通过慢任务期间连续聊天，也要通过“全球新闻 → 国内新闻 → 最近三天 → 只看科技”的连续修正，最终有效目标为“搜索最近三天的国内科技新闻”；原任务无取消/重启，未指定的条件保留，独立聊天不影响目标。只解锁输入框、只把消息排到旧任务后面，或仍交付全球新闻，都不算完成。
10 USER SCENARIOS / EXPECTED OUTCOMES

全部实现后，可以这样使用

以下 10 个用例把操作、可见效果和边界写在一起，便于后续演示与验收。UC01–UC03、UC05–UC06 属于第一优先级：持续聊天及同任务要求合并；UC04、UC07–UC10 随完整任务管理交付。均为预期效果，尚未实现。新闻检索、旅行等业务例子以相应工具已配置可用为前提。

UC01 / 第一优先 · A1

任务还在跑，顺便聊别的问题

用户操作：让 A 整理旅行方案，看到查询仍在执行，直接在同一输入框问“红眼航班是什么意思？”

预期效果：立即出现新的问答气泡，正常解释概念；A 的工具与计划继续更新，完成后另行交付。

关键边界：新问题不会变成停止按钮，也不会重新启动 A；这条聊天不继承 A 的未完成计划去继续执行。

UC02 / 第一优先 · A1 / A8

一口气追加几句，仍保持上下文

用户操作：A 执行期间先问“红眼航班是什么”，再问“带小孩适合吗”，继续补充“孩子六岁，容易晕车”。

预期效果：三条消息都能发送；普通聊天按顺序回复，后续回答能使用前面的解释与补充信息，不等待 A 结束。

关键边界：上一条聊天尚未完成时显示等待；不无限并发调用模型。消息队列满时明确提示，不静默丢弃输入。

UC03 / 第一优先 · A4 / A8

只停止一条回复，其他执行继续

用户操作：A 与一条普通聊天同时进行，对聊天点击“停止本条回复”；或者该聊天因网络问题失败。

预期效果：只结束/标记这条聊天，A 保持运行；其他已接收消息保留，后续仍可继续聊天，各自错误和调用记录独立。

关键边界：首期的停止是结束对应响应流，不保证回滚工具副作用，也不宣称能够从 Checkpoint 恢复。

UC04 / 完整任务管理 · A2

随时问进度，马上看到真实状态

用户操作：问“任务 A 到哪一步了？”或“所有任务现在怎么样？”

预期效果：展示 A 的实际完成步骤、当前工具、最近进展及其他任务状态；执行配额已满也能查询。

关键边界：状态查询不排到长任务后面，不要求模型猜测进度；尚无可核验总量时不编造完成百分比。

UC05 / 第一优先 · A3

全球新闻改成国内，最终只交付国内新闻

用户操作：先说“帮我搜索全球的新闻”，任务 A 运行中再说“就搜索国内的就好了”。

预期效果：自动把第二句关联到 A，将范围由全球替换为国内；确认收到并在安全边界应用，最终结果只列国内新闻。

关键边界：全球查询尚未开始时直接按国内搜索；已经发出则等待返回、筛选国内内容并按需补搜。无需取消重跑 A，也不新建第二个搜索任务；若 A 已提交终态，则明确创建基于原结果的修订任务。

UC06 / 第一优先 · A1 / A3

连续修正条件，穿插聊天仍能接上任务

用户操作：A 从全球改为国内后，再补充“最近三天的”“只看科技”；中间还可以问“什么叫科技独角兽公司？”

预期效果：A 的最新目标合并为“搜索最近三天的国内科技新闻”；普通问题独立回答，随后明确的搜索条件仍关联 A，不丢失前面的国内范围。

关键边界：只替换被明确修正的条件，其余保留；保留原始消息和控制记录，已完成资料不删除。多个候选任务或无法判定指代时先询问，不擅自合并。

UC07 / 完整任务管理 · A4

先暂停，补充信息后再恢复

用户操作：说“暂停任务 A，我先确认日期”；稍后补充日期并点击恢复。

预期效果：先显示“暂停中，等待当前工具/子代理结束”，Checkpoint 保存后显示“已暂停”；恢复后重新排队领取执行槽，继续同一任务。

关键边界：暂停不意味着任意工具立刻结束；补充信息本身不自动恢复。当前同步子代理需先收敛完成，再在主图暂停。

UC08 / 完整任务管理 · A4 / A7

取消任务，并看清已经发生的操作

用户操作：任务 A 正在写文件或发送已授权预订请求时，点击“取消任务 A”。

预期效果：禁止继续发起新操作，显示“取消中”；运行中操作结算后进入“已取消”，列明已保存文件、已确认结果或待核对操作。

关键边界：取消 Agent 不等于取消订单或回滚文件；结果不明的请求不自动重复发送。需要继续时创建引用既有成果的新任务。

UC09 / 完整任务管理 · A5

两个任务并行，第三个排队

用户操作：同一会话先启动 A 整理路线、B 整理资料，再提交 C；分别查看或调整 A、B。

预期效果：默认两个执行槽下 A、B 并发，C 显示排队；仍可聊天。任务计划、工具进度、结果和文件按任务区分，不相互覆盖。

关键边界：两个任务可以各自写自己的 result.txt；需要共用同一成果时通过明确引用与冲突规则处理，不让共享目录任意并发写入。

UC10 / 完整任务管理 · A6 / A7 / A8

刷新、断网或服务重启后接着处理

用户操作：A 执行中刷新页面，或网络短暂中断；服务重启后再次打开会话。

预期效果：重新加载服务端任务快照与遗漏事件；安全任务从持久现场续跑，已暂停任务仍保持暂停，结果通知不会重复出现。

关键边界：重启不等于所有任务无条件重试；外部写操作结果未知时显示“需要核对后恢复”，避免重复预订或重复写入。

02 / ARCHITECTURE

控制面独立，执行仍由 Deep Agents 驱动

这里的全双工指应用层可同时接收消息和推送任务事件。HTTP POST + SSE 已满足目标，无需为“全双工”额外引入 WebSocket、Celery、Redis 或第二层 LangGraph 工作流。

候选路线适用依据局限 / 结论
A · FastAPI 内嵌任务运行时

首期运行边界

  • 默认后台任务并发 N=2，有限队列；另留交互模型通道。模型与工具还有全局限流，防止子代理把并发预算放大。数字为提案配置，实施压测后校准。

03 / ROUTING & CONTRACTS

消息先确定用途，再确定目标

显式 UI 动作和命令优先；自然语言结合会话上下文进行受限结构化分类，返回候选意图、目标与修改内容，由 Controller 校验后提交。语义明确的同任务补充应自动合并到当前任务，独立问题进入 CHAT；不能把所有新消息一律当作闲聊或一律注入任务。

04 / STATE OWNERSHIP

三类状态，各自有明确所有者

01 / CONVERSATION STATE

面向用户的对话

messages、任务引用、结果通知、事件游标、conversation revision。Controller 负责追加与排序；任务完成只追加通知，不改写聊天模型的执行上下文。

02 / EXECUTION STATE

Agent 的执行现场

完整模型/工具消息、todos、摘要、计数、directive revision、applied cursor、checkpoint namespace。由 LangGraph Checkpointer 保存；只有当前 Worker 可调用执行/恢复/更新 API。

03 / TASK STATE

任务的业务生命周期

状态、意图、租约、attempt、超时预算、进度快照、控制日志、结果引用、副作用状态。由 Task Manager 通过事务和 CAS 管理；不是另一份 Agent 历史。

冲突点约束与实现策略
同一 Thread 双写每任务独立 execution_thread_id，不等于 conversation_id。Task Manager 唯一领取 + Worker 持锁；API 不并发调用 agent.astream / aupdate_state。恢复前确认旧 Worker 已结束。
普通聊天与后台执行Conversation 的消息锁只保护短事务；模型生成持单独的交互锁，绝不持 Conversation DB 锁。结果通知可并行入库，按 message/event sequence 排序。
同一任务的并行分支使用 LangGraph 自带子图 namespace 与 reducers；每个执行分支记录自己的 control cursor。控制日志采用可重读序列，不让一个子代理“抢走”其他分支的新指令。
工作区共享新任务默认使用 workspace/tasks/{task_id}/，同任务子代理继承同一目录；旧聊天沿用现有根目录。跨任务成果通过显式 artifact 引用导入。文件写入需规范化路径 + 资源互斥；根目录旧工具与任务目录重叠时也必须互斥。
闭包捕获与全局 profile现有 backend、tools、ContextWindowMiddleware 都捕获 settings/workspace。增加按执行作用域构建的 AgentFactory，不复用绑错目录的工具闭包；保留已有 _BUILD_LOCK，避免 profile 注册和并发构图串用后端。
日历与预订归属日历下载要从 artifact index 定位任务文件，保留旧 URL；新预订授权绑定 conversation + task + quote + control/turn，恢复时重新校验，不能把旧确认长期放进 configurable 后重复使用。
Checkpoint 只保存图状态，不替代外部状态隔离。文件、预订、模型并发配额、回调收集器都必须检查作用域。即使两个任务使用不同 thread_id，也不能同时无锁覆盖同一个文件。
05 / MID-RUN STEERING

在下一次决策前，让新约束成为执行上下文

Steering 使用持久控制日志 + Middleware，继续同一次 Agent 执行。它不调用 task.cancel，不替换 execution_thread_id，也不以取消重启模拟实时交互。正常 Steering 可以促使 Agent 重规划，但保留已经完成的事实与成果。

  1. 持久接收。Controller 校验目标、revision 与幂等键；在同一事务内写 controls、task revision 和 control.received 事件，随后唤醒 Worker。
  2. 安全边界读取。abefore_model 读取未应用控制，按 task sequence 得到新 directive revision。aafter_model 再检查一次，覆盖模型调用期间新到达的指令与终态竞争。
  3. 合并用户级要求。执行状态保存结构化 directives、稳定 control_id 和 requirement revision。最新明确修正替换冲突条件，其余条件保留；生成有效任务视图供模型、工具选择和交付校验共用。原始目标作为历史保留，但不要求模型继续遵守已被替换的“全球范围”；用户文本不提升为系统授权。
  4. 防止陈旧工具继续。工具 wrapper 在实际启动前检查取消/暂停意图和 planning revision。Steering 已到达而本次工具计划仍基于旧 revision 时，未启动调用返回配对的“因新约束推迟”ToolMessage，下一模型边界重新决策；已启动调用按原语义结算。
  5. Checkpoint 后确认。applied cursor / directives 由图返回状态更新并持久化。Worker 从 checkpoint 事件或显式读取核实后，写 control.applied。崩溃后以 checkpoint cursor 补发确认，不永久破坏性出队。

与现有 Middleware 的衔接

  • 控制字段与执行历史分开。不要直接把每条 STEER 当作新的顶层 HumanMessage：现有 plan 初始化、latest-user 判断、工具选择和交付校验可能错误切换任务或重置计数。
  • 增加统一 effective_task_request 视图：原始任务 + 有序追加/替换约束。约束作为有来源的用户内容进入模型请求，并参与 token preflight；压缩后仍从持久字段恢复生效约束，不能只依赖历史摘要“记住它”。
  • 在每个尚未提交的最终结果上执行 revision 屏障：若已有已接受的修正尚未应用，不提交旧版本成功结果，先应用修正并继续决策。Controller 接收修正与任务终态提交通过同一任务 revision 仲裁；终态先提交时明确转为新修订任务。
  • “预算改为 3000”是有序约束更新；“保留已完成成果”保持现有不可改写记录。互相冲突且无法确定的新旧要求标为需要澄清，不让模型自行扩大授权。
  • General-purpose 子代理不会自动继承任意主 Middleware。通过现有 HarnessProfile.extra_middleware 安装控制读取和工具 gate，或者显式配置；暂停节点仅用于主 Agent，避免子代理与并行 ToolNode 内直接 interrupt。
  • 每个活跃分支独立记录 applied cursor。事件带 namespace 与 revision；分支生效先展示分支确认，全任务“已应用”仅在当前活跃分支均已采用或已结束后给出。新启动分支从最新已接收约束初始化。
机制用途不应混淆的语义
控制日志 + Middleware在模型/工具执行边界读取新增约束，更新同一执行。STEER 通常不需要 Interrupt，也不等待另一个用户回复才能继续。
interrupt()
Command(resume=...)		可持久挂起并等待外部输入。首期用于主 Agent 的用户暂停；保留作为既有人审/HITL 扩展点。这是节点内部主动让出执行，不是从 HTTP 请求强行打断 Tool。恢复会重跑节点开头，必须稳定命中同一个 interrupt。

暂停的首期承诺

PAUSE 不强行取消当前工具。正在运行的同步 task 子代理视为一个 in-flight Tool：允许本次委派及其内部工具收敛完成，然后在主图下一边界暂停；界面明确显示“暂停中，等待子代理结束”。其他尚未开始的主图工具调用被 gate 推迟。Steering 仍可在子代理模型边界生效；CANCEL 则传播整个任务树的禁止新操作信号。

这是稳定 MVP 的显式限制：没有承诺子代理内部立即持久挂起，也没有承诺任意工具的毫秒级中断。若业务要求暂停能在任意子代理内部生效，必须先通过嵌套 checkpoint、并行工具重放与副作用测试，再扩展暂停边界。

恢复、控制竞争与重放规则
  • 控制日志按 seq 有序处理；CANCEL 一经接受就封闭执行，后续 RESUME 返回 409。STEER 不自动恢复 PAUSED；在队列中保留到恢复后的下一决策边界。
  • PAUSING 时的 RESUME 记为“挂起后恢复”的意图，先确认暂停 checkpoint，再排队恢复；禁止并发创建第二个 Worker。重复 PAUSE/RESUME 返回已存在的控制结果。
  • 保存 pause_epoch、boundary_key 与 interrupt ID。恢复前不要清掉 pause marker；重放时必须走到原 interrupt 并消费 resume 值，之后再提交清除标记。
  • 匹配控制类型与 interrupt kind，只恢复指定 ID；不能用通用 resume=true 一并批准其他人工审核。
  • SUCCEEDED / FAILED / CANCELLED 是终态。若用户要继续已取消任务，创建带 source_task_id 的新任务；可显式引用已有成果，不复用被取消 Thread 的待执行操作。
  • 终态 CAS 与控制接收共用任务 revision：谁先提交决定结果。终态已提交后到达的控制返回 TASK_ALREADY_TERMINAL，避免“已收到但永不生效”。
07 / PERSISTENCE & RELIABILITY

恢复执行，也恢复对“不确定”的认识

持久目录建议位于 .assistant-private/runtime/，与可读写工作区分离；TaskStore 与官方 Checkpointer 使用独立数据库连接/文件。Docker 必须挂载私有运行目录和工作区两类持久卷。

数据 / 建议最小表关键字段与唯一约束
conversations / messagesconversation_id、message_id、sequence、revision、task_ref；唯一 client_message_id，保存输入指纹防同键异内容。
taskstask_id、conversation_id、execution_thread_id、status、desired_action、revision、attempt、lease_owner / epoch、heartbeat、remaining_budget、resume_mode、result_ref；并记录 accepted_requirement_seq、applied_requirement_seq、effective_task_request 与最终交付对应的 requirement revision。

events / notifications会话内递增 event_seq、event_id、task_id、attempt_id、payload、dedup_key；终态通知以 task_id + terminal revision 去重。
effects / artifacts稳定 operation_id、task_id、checkpoint_ns、tool_call_id、tool、args_digest、STARTED / SUCCEEDED / UNKNOWN、receipt/result_ref；artifact index 记录路径、版本、哈希与作用域。
官方 checkpoint 数据完整图状态、pending writes、Thread / namespace、interrupt。采用官方 SQLite saver schema 与序列化，不复制到自定义任务表。

重启后的判定流程

  1. 取得唯一运行时所有权。校验 schema 版本和持久卷；读取非终态任务，确认原进程已结束，旧执行者不得继续写 checkpoint。正常停机先停止领取，使用 RunControl drain，保存收敛结果再关闭 saver。
  2. 先读执行现场。核对 latest checkpoint、pending interrupt、task revision、effect ledger 与既有预订库。根据 checkpoint 中 control cursor 修补应用确认和事件。
  3. 按恢复模式继续。QUEUED 重新领取；PAUSED 保持暂停；WAITING_INPUT 保留待输入；已 drain / 安全崩溃且无未知写操作的任务从原 Thread 的 checkpoint 继续。
  4. 不明写操作先阻塞。外部请求可能成功但本地未记录时标记 UNKNOWN，任务进入 RECOVERY_REQUIRED；查供应商回执或由用户对账。已经接受 CANCEL 的任务不能被自动恢复为 RUNNING。
  5. 补齐持久结果。图已完成但 TaskStore 尚未更新时，用 checkpoint 与交付记录修复终态、结果通知；消息与事件都使用稳定幂等键，避免重复交付。
TaskStore 与 Checkpointer 之间没有分布式事务。用“持久输入日志 → 图内幂等应用 → checkpoint 核实 → TaskStore 确认”的协议弥合间隙。control.applied 之前崩溃，可能重读但不能重复生效；Checkpoint 之后 ACK 丢失，恢复时补发。不承诺外部副作用 exactly-once。
副作用类型取消 / 崩溃 / 重试策略
纯计算、只读 HTTP有界超时、可合作取消；仅已知可安全重复的错误使用有限指数退避。重试前复核 CANCEL/PAUSE/revision。
文件写入、编辑、删除、ICS持久 operation_id；写入前记录预期版本，原子替换与哈希核对，文件锁覆盖实际写入区间。编辑/删除不按“同参数即可幂等”处理；随机 ICS ID 改为由操作 ID 确定，并能核对崩溃后文件。同步线程未退出前不宣称已取消。
预订与外部创建继续使用现有 TravelStore 的报价归属、精确确认、CAS claim 与 UNKNOWN 状态；若供应商支持幂等键则衔接。取消执行不会取消订单；响应不明不自动重试。
取消与工具启动竞争工具开始登记与控制接收按任务 revision 仲裁。已被认定 STARTED 的操作可能继续完成；CANCEL 提交后未开始的操作被拒绝。后续事件明确回报“已完成/未执行/结果未知”。

超时、限额和故障不扩大权限

保留模型请求 timeout、工具 timeout、graph recursion 与调用次数上限；增加任务累计 active-time / model / tool 预算，跨 pause/resume/attempt 持久累计，暂停与排队不消耗 active-time。恢复不能重置所有预算从而无限执行；超限进入 RECOVERY_REQUIRED 或 FAILED，并给出可恢复条件。可恢复超时必须确认没有活跃写操作和未知副作用，才允许继续。

服务停机若超过 graceful drain 时限，按崩溃路径恢复；GraphDrained 属于控制收敛，不应被现有 except Exception 映射成 MODEL_ERROR。图/依赖/提示词版本变化记录 execution fingerprint，遇到不兼容 checkpoint 进入人工迁移流程，不盲目续跑。
